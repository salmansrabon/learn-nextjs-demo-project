Chapter 1 — Frontend Project Overview

We build the frontend of a User Management Mini App. The backend is the kitchen (processes data, talks to the database), the frontend is the dining area (forms, buttons, tables), and the API is the waiter between them.

1.1 React & Next.js Overview

React is a JavaScript library (by Meta, 2013) for building UIs from reusable components. Its key idea is the Virtual DOM: you update state, React calculates the smallest DOM change and applies it. React handles only rendering and state — routing and structure are up to you.

Next.js is a React framework (by Vercel, 2016) that fills those gaps: file-based routing, server-side rendering, and production optimisation. This project uses the App Router (Next.js 13+), where every folder inside app/ becomes a URL route.

TopicReact (plain)Next.js
TypeUI libraryFull framework on top of React
RoutingManual (React Router)Built-in, file-based (folders = routes)
RenderingClient-side only (CSR)CSR + SSR + SSG + ISR, chosen per page
SEOPoor — empty HTML until JS loadsExcellent — HTML ready before render

API routesNot includedBuilt-in backend endpoints in the same project

1.3 Why Next.js is Popular

  • Performance by default — code splitting, lazy loading, image optimisation built in.
  • SEO-friendly — server renders HTML before the browser, so search engines index content.
  • Zero-config routing — create a file in app/, it becomes a URL.
  • Flexible rendering — choose SSR, SSG, or CSR per page.
  • Full-stack in one project — built-in API routes; easy deployment (Vercel or any Node host).
  • Industry adoption — Netflix, TikTok, Twitch, Notion, and thousands of startups.

1.6 Setting Up the Practice Playground

Step 0 — How App Router Routing Actually Works

Everything else in this section only makes sense once one rule clicks: inside the app/ folder, folders are URLs, and a file named exactly page.jsx is what makes a folder actually render something. A folder with no page.jsx inside it is not a route — Next.js just ignores it (or uses it for plain helper files, as you'll see with ThemeContext.jsx below). And if the app/ folder doesn't exist at all, or contains no page.jsx anywhere, next dev fails immediately with "Couldn't find any pages or app directory" — there is nothing for it to serve.

Here is the entire file tree you'll build across this chapter and the next two, annotated with the URL each page.jsx produces:

Three things worth noticing in that tree: (1) [id] in square brackets is a dynamic segment — one file matches /hooks/use-params/5, /42, /100, anything; (2) use-context/ThemeContext.jsx sits right next to page.jsx inside the same folder but produces no route of its own, because it isn't named page.jsx — folders only become URLs when a page.jsx is present; (3) components/ lives outside app/ entirely, so nothing in it is ever treated as a route no matter what it's named — more on that in Step 4.

You'll create this tree gradually: the shell (layout.jsx, globals.css, the shared components, the home page) in this section, then one lesson folder per topic as you reach it in Chapters 2 and 3.

Step 2 — Configuration Files

next.config.js is how Next.js itself is configured — image domains, redirects, experimental flags, and so on. This project needs none of that, so the file exists (Next.js expects to find it) but stays empty:

// next.config.js — empty, same as the real project
/** @type {import('next').NextConfig} */
const nextConfig = {};
module.exports = nextConfig;

jsconfig.json is unrelated to Next.js routing — it's a plain editor/compiler hint that lets you write import PageHeader from '@/components/PageHeader' instead of counting ../../../ back up to the project root. "@/*": ["*"] means "@/ maps to the project root," so @/components/PageHeader resolves to components/PageHeader.jsx and @/lib/x would resolve to lib/x.js, no matter how deeply nested the file doing the importing is (e.g. app/hooks/use-params/[id]/page.jsx):

// jsconfig.json
{
  "compilerOptions": {
    "baseUrl": ".",
    "paths": { "@/*": ["*"] }
  }
}

Step 4 — Shared Components (the components/ folder)

components/ has zero special meaning to Next.js — unlike app/, nothing here becomes a route no matter what you name the files or how you nest them. It's just a folder of ordinary React components that you import by hand wherever you need them, using the @/components/... alias from Step 2. Convention, not magic — you could call this folder ui/ or shared/ and nothing would break.

Build the one component every lesson page below will import — a small header with a "back to home" link:

// lib/readSource.js — reads a file straight off disk at render time, so the
// code panel below always shows the real, currently-saved source
import fs from 'fs';
import path from 'path';

export function readSource(...relativePaths) {
  return relativePaths
    .map((rel) => {
      const contents = fs.readFileSync(path.join(process.cwd(), rel), 'utf-8').trimEnd();
      return `// ${rel}\n${contents}`;
    })
    .join('\n\n');
}
// components/CodePanel.jsx — renders the string readSource() returns
export default function CodePanel({ label = 'Source', code }) {
  return (
    <div className="code-panel">
      <div className="code-panel-label">{label}</div>
      <pre className="code-block"><code>{code}</code></pre>
    </div>
  );
}

Important: readSource() uses Node's fs module, which only exists on the server. Never import it from a file that starts with 'use client' — the build will fail with "Module not found: Can't resolve 'fs'". That's why every lesson below splits into two files: a plain page.jsx (a Server Component — no 'use client' — free to call readSource(), renders PageHeader + Theory + <Demo /> + CodePanel) and a Demo.jsx (the thing being demonstrated). For interactive lessons, this split is required — Demo.jsx is marked 'use client'. For non-interactive lessons, the split is done anyway, for a second reason: the code panel should show only "how this is created and used," never the PageHeader/Theory/CodePanel wrapper around it — reading page.jsx itself would show the panel's own wiring, which is noise. So readSource() is always pointed at Demo.jsx (plus any component file it imports), never at page.jsx.

Chapter 2 — React JSX Syntax & Events

2.1 What is a React Component?

A component is a JavaScript function that returns JSX — a reusable, self-contained piece of UI, like a custom HTML tag. In the real project Navbar, Loading, ErrorMessage, UserTable, UserForm, and every page are components. Two rules:

  1. The function name must start with a capital letter (lowercase is reserved for HTML tags).
  2. It must return exactly one root element.

No dedicated playground page for this definition alone — you'll write your first real one in 2.2 below.

2.2 Creating a Component — 4 Steps

  1. Create a file named after the component: components/ErrorMessage.jsx
  2. Write a function starting with a capital letter (it can receive props)
  3. Return JSX (one root element)
  4. Export it with export default

Build it — playground: components/WelcomeCard.jsx + app/creating-component/page.jsx

3.5 Lifecycle: Mounting, Updating, Unmounting

Build it — playground: app/hooks/use-effect/Demo.jsx + app/hooks/use-effect/page.jsx

// app/hooks/use-effect/Demo.jsx
'use client';
import { useEffect, useState } from 'react';

function Timer({ onLog }) {
  const [count, setCount] = useState(0);

  // MOUNTING + UNMOUNTING — empty dependency array runs once, cleanup on unmount
  useEffect(() => {
    onLog('✅ mounted');
    return () => onLog('❌ unmounted');
  }, []);

  // UPDATING — re-runs on mount, then again every time count changes
  useEffect(() => {
    onLog(`🔄 count updated: ${count}`);
  }, [count]);

  return (
    <div className="demo">
      <p>Count: {count}</p>
      <button onClick={() => setCount((c) => c + 1)}>Increase</button>
    </div>
  );
}

4.2 The 'use client' Directive

In the App Router, all components are Server Components by default — they run only on the server and cannot use useState/useEffect, event handlers, or browser APIs (localStorage, window). Adding 'use client' as the very first line makes it a Client Component. Compare the project's two kinds of files:

// app/login/page.jsx — CLIENT component: needs hooks + events + localStorage
'use client';                                  // must be line 1, before imports
import { useState } from 'react';
import { useRouter } from 'next/navigation';
...

// app/layout.jsx — SERVER component: no directive, no hooks, just structure
import 'bootstrap/dist/css/bootstrap.min.css';
import './globals.css';
export const metadata = { title: 'User Management Mini App' };  // server-only feature
export default function RootLayout({ children }) {
  return <html lang="en"><body>{children}</body></html>;
}

Hydration: even Client Components get a pre-rendered HTML shell from the server for fast first paint; React then "hydrates" it in the browser. That is why Navbar reads localStorage inside useEffect — reading it during render would differ between server and browser and cause a hydration mismatch (you saw a concrete example of this exact bug in the playground's useRef section, 3.9).

Golden rule: a Server Component can render a Client Component (the project's RootLayout renders every client page via {children}); a Client Component cannot import a Server Component. Tip: keep 'use client' as deep in the tree as possible — less JavaScript sent to the browser.

Chapter 5 — Advanced React Concepts

5.1 Re-render Behaviour

React re-renders a component when: its state changes, its props change, its parent re-renders (even with unchanged props), or a Context value it consumes changes. In this project: every time loading toggles in LoginPage, the whole page re-renders — including <ErrorMessage /> whose message prop didn't change. Harmless here, but the fix is 5.5.

5.2 Prop Drilling

Passing data through layers that don't use it, just to reach a deep child. This project avoids it two ways: Navbar reads localStorage directly (works, but not idiomatic React — see 5.3), and AdminUsersPage passes props exactly one level down (users, onDelete → UserTable), which is fine and not drilling.

5.3 Context API

React's built-in shared store: create → provide → consume. Not used in this project — but you already built and ran this exact three-step pattern in the playground's useContext example (3.12), where ThemeContext.jsx shared a theme value with a deeply nested consumer, no props involved. Here is the AuthContext that would replace the localStorage reads in Navbar and every page guard — same shape, different value:

import { createContext, useContext, useState } from 'react';

// 1. create
export const AuthContext = createContext(null);

// 2. provide — mirrors what app/login/page.jsx currently does inline
export function AuthProvider({ children }) {
  const [user, setUser] = useState(null);
  const login = (userData, token) => {
    localStorage.setItem('token', token);
    localStorage.setItem('user', JSON.stringify(userData));
    setUser(userData);
  };
  const logout = () => {
    localStorage.removeItem('token');
    localStorage.removeItem('user');
    setUser(null);
  };
  return <AuthContext.Provider value={{ user, login, logout }}>{children}</AuthContext.Provider>;
}
// wrap {children} with <AuthProvider> in app/layout.jsx

// 3. consume — Navbar drops its useEffect + localStorage code entirely
const { user, logout } = useContext(AuthContext);

5.4 Controlled vs Uncontrolled Components

Controlled — React state owns the value; used by every form in this project:

// app/login/page.jsx — React always knows the field content
<input
  type="email"
  name="email"
  value={formData.email}          // value comes FROM state
  onChange={handleChange}         // every keystroke updates state
  className={`form-control ${errors.email ? 'is-invalid' : ''}`}
/>

Uncontrolled — the DOM owns the value, read via useRef only when needed (defaultValue, no onChange). Simpler, but you lose live validation and easy reset — which is exactly why this project's validation-heavy forms are all controlled.

5.5 React.memo

Wraps a component and skips its re-render when props are unchanged (shallow comparison). Not used in this project — but you already used it in the playground: the Child button in the useCallback example (3.10) is wrapped in memo(), which is exactly why typing in the text box next to it never logged another "Child rendered." The best candidates in the real project are its pure display components:

// components/ErrorMessage.jsx — one-line improvement
import React from 'react';
const ErrorMessage = React.memo(function ErrorMessage({ message }) {
  if (!message) return null;
  return <div className="alert alert-danger py-2">{message}</div>;
});
export default ErrorMessage;
// Now toggling 'loading' in LoginPage no longer re-renders ErrorMessage.
// UserTable is the biggest win — a large table with unchanged 'users' between renders.

5.6 Error Boundaries

Catch errors thrown during rendering in the child tree and show a fallback instead of a blank page (try/catch doesn't work in the render cycle). Must be a class component. In this project, if UserTable threw while mapping a bad row, the whole admin page would go blank — wrapping it in a boundary (or simply adding a per-route error.jsx, section 4.8) shows "Something went wrong" with a retry button instead.

const API_URL = process.env.NEXT_PUBLIC_API_URL || 'http://localhost:5000';

  baseURL: API_URL,
  headers: { 'Content-Type': 'application/json' },

// REQUEST INTERCEPTOR — adds JWT Bearer token before every request
api.interceptors.request.use((config) => {
  // typeof window check: localStorage only exists in browser, not during SSR
  const token = typeof window !== 'undefined' ? localStorage.getItem('token') : null;
  if (token) {
    config.headers.Authorization = `Bearer ${token}`;
  }
  return config;
});

// RESPONSE INTERCEPTOR — handles expired/invalid tokens globally
api.interceptors.response.use(
  (response) => response,
  (error) => {
    if (error.response?.status === 401 && typeof window !== 'undefined') {
      localStorage.removeItem('token');
      localStorage.removeItem('user');
      window.location.href = '/login';
    }
    return Promise.reject(error);
  }
);

// app/login/page.jsx — the actual file
'use client';
import { useState } from 'react';
import Link from 'next/link';
import { useRouter } from 'next/navigation';
import { login } from '../../services/authService';
import { validateLoginForm } from '../../utils/validation';
import ErrorMessage from '../../components/ErrorMessage';

export default function LoginPage() {
  const router = useRouter();

  const [formData, setFormData] = useState({ email: '', password: '' });
  const [errors, setErrors] = useState({});
  const [loading, setLoading] = useState(false);
  const [apiError, setApiError] = useState('');

  const handleChange = (e) => {
    const { name, value } = e.target;
    setFormData((prev) => ({ ...prev, [name]: value }));
    if (errors[name]) setErrors((prev) => ({ ...prev, [name]: '' })); // clear error while typing
  };

  const handleSubmit = async (e) => {
    e.preventDefault();
    setApiError('');

    const validationErrors = validateLoginForm(formData);
    if (Object.keys(validationErrors).length > 0) {
      setErrors(validationErrors);
      return;
    }

    setLoading(true);
    try {
      const result = await login(formData);

      // store credentials for subsequent requests (read by api.js interceptor)
      localStorage.setItem('token', result.data.token);
      localStorage.setItem('user', JSON.stringify(result.data.user));

      // role-based redirect
      if (result.data.user.role === 'admin') {
        router.push('/admin/users');
      } else {
        router.push('/profile');
      }
    } catch (err) {
      setApiError(err.response?.data?.message || 'Login failed. Please check your credentials.');
    } finally {
      setLoading(false);
    }
  };

  return (
    <div className="min-vh-100 bg-light d-flex align-items-center justify-content-center">
      <div className="card shadow-sm" style={{ width: '100%', maxWidth: '400px' }}>
        <div className="card-body p-4">
          <h1 className="card-title text-center mb-4 h4">Login</h1>

          <ErrorMessage message={apiError} />

          <form onSubmit={handleSubmit}>
            <div className="mb-3">
              <label className="form-label">Email</label>
              <input
                type="email"
                name="email"
                value={formData.email}
                onChange={handleChange}
                className={`form-control ${errors.email ? 'is-invalid' : ''}`}
                data-testid="login-email"
              />
              {errors.email && <div className="invalid-feedback">{errors.email}</div>}
            </div>

            <div className="mb-4">
              <label className="form-label">Password</label>
              <input
                type="password"
                name="password"
                value={formData.password}
                onChange={handleChange}
                className={`form-control ${errors.password ? 'is-invalid' : ''}`}
                data-testid="login-password"
              />
              {errors.password && <div className="invalid-feedback">{errors.password}</div>}
            </div>

            <button type="submit" disabled={loading}
                    className="btn btn-primary w-100 mb-3" data-testid="login-submit">
              {loading
                ? <><span className="spinner-border spinner-border-sm me-2" role="status" />Logging in...</>
                : 'Login'}
            </button>
          </form>

          <p className="text-center text-muted small mb-0">
            No account? <Link href="/register">Register</Link>
          </p>
        </div>
      </div>
    </div>
  );
}
