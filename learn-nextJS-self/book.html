Chapter 2 - React JSX Syntax and Events

These lessons build the basic React mental model: a component is a function, JSX is the markup returned by that function, props pass data in, state changes the UI, and events respond to user actions.

2.1 Creating a Component

Build a reusable component in components/WelcomeCard.jsx, then render it from the route file. The function name starts with a capital letter and returns JSX.

2.2 Shared Lesson Header

Each lesson page uses the same header component so navigation, title, and description stay consistent.

2.3 Fragments

A React component must return one root value. A Fragment groups sibling elements without adding an unnecessary wrapper element to the DOM.

2.4 Sibling Components

A page can compose multiple child components inside one parent Fragment. In this example, PageHeader and both WelcomeCard instances are sibling children nested inside CreatingComponentPage.

2.5 JSX Syntax Rules

JSX looks like HTML, but it is JavaScript. Use className, close every tag, use braces for JavaScript expressions, and return one root element.

2.6 Conditional Rendering

JSX does not allow if/else directly inside markup. Use && for optional UI, a ternary for exactly two choices, and null to render nothing.

2.7 Rendering Lists

Use map() to turn an array into JSX. Give every repeated element a stable key so React can track changes correctly.

2.8 Event Handling

Event handlers are functions passed to JSX props such as onClick, onChange, and onSubmit. Form submit handlers usually call preventDefault().

Chapter 3 - Component Lifecycle and Hooks

Hooks let function components remember values, run side effects, navigate, read route params, and reach DOM nodes directly. These five are the ones the application in chapter 4 actually uses, so learn them properly before reaching for anything else.

React has more hooks than these - useContext, useReducer, useMemo and useCallback among them. They solve problems you have not met yet: sharing state across a deep tree, and avoiding work that is not yet slow enough to be worth avoiding. Chapter 5 covers what they do, which is what an interviewer will ask.

3.1 useState

useState stores data that affects rendering. Calling the setter schedules a re-render with the new value.

Real-life use: Use it for a controlled form field, a shopping-cart count, a show/hide menu, or a loading and error message that must change on screen after the user acts.

3.2 useEffect

useEffect runs side effects after render. The dependency array controls when the effect runs again, and the function it returns is the cleanup.

Real-life use: Use it to load a user after a page opens, subscribe to a WebSocket, update the document title, or add a browser event listener and remove it during cleanup. Chapter 4 keeps this exact shape for every page it builds and only swaps fetch for axios.

3.3 useRouter

useRouter from next/navigation performs programmatic navigation from a Client Component.

Real-life use: Use it after a successful login to send someone to their dashboard, after saving a form to return to the list, or to go back when a modal-like detail page is closed.

3.4 useParams

Dynamic route folders such as [id] create URL params. useParams() reads those values in a Client Component.

Real-life use: Use it on a product page such as /products/42, a profile such as /users/maya, or an order page where the URL identifies which record the component should load.

3.5 useRef

useRef can point to a DOM element or hold a mutable value that does not trigger a re-render when it changes.

Real-life use: Use it to focus the first invalid input, play or pause a video, remember the previous value, or keep an interval ID so cleanup can cancel it without updating the UI.

4.1 Calling a GET API and rendering it

Practice first, in a throwaway page at app/practice/page.jsx. No backend needed. Every data-loading page in this chapter is the same three pieces: state to hold the response, an effect to start the request, and a render that maps over the state.

'use client' appears here for the first time. Files under app/ are Server Components by default, and a Server Component has no useState, no useEffect and no event handlers, because no browser is involved. Every page you write in this chapter needs all three, so every one of them is a Client Component.

The effect ends in [] for a reason. With no dependency array an effect runs after every render, and calling the setter causes a render, so the component would fetch forever.

4.2 Loading and error states

A request has three outcomes and the UI must show all three: waiting, failed, or here is the data. Section 4.1 rendered only the third, which is why its list flashed empty first.

The trap worth memorising: fetch() does not throw on 404 or 500. It rejects only when the request never completed at all. A 404 arrives as a perfectly successful promise with res.ok === false, so you must check it and throw yourself. finally then guarantees the loading flag clears on both paths.

This is one of the main reasons the app switches to axios in 4.5, which rejects on any non-2xx by itself.

4.5 The axios client and the services layer

You wrote two fetch calls in 4.1 and 4.2, so this comparison is not abstract:

fetchaxios
Reading the bodyawait res.json()res.data, already parsed
404 and 500Resolves - you must remember res.okRejects, so catch runs
Query paramsBuild the string yourselfA params object, URL-encoded for you
The auth headerWritten at every call siteOne request interceptor

An interceptor is a function axios runs on every request, or every response, before your code sees it. The request interceptor attaches Authorization: Bearer <token> to everything - which is why no page in sections 4.10 to 4.14 ever mentions that header. The response interceptor watches for 401 and clears the dead session once, centrally.

Both guard with typeof window !== 'undefined', because localStorage does not exist while Next.js renders on the server. The response interceptor still re-rejects the promise after cleaning up - swallow the error there and the calling page waits on a spinner forever.

The three service files exist so that no page ever contains a URL. When an endpoint moves you edit one line in one file, and the pages stay readable: getAllUsers({ page, limit: 5, search }) says what is happening.

The request is the easy half. What is new is the response: data.data holds a token and a user, and everything after this depends on them.

4.9 The navbar, and the hydration trap

Next.js renders your page twice: once on the server to produce HTML, then again in the browser. React compares the two and throws a hydration mismatch if they differ. Since localStorage does not exist on the server, a component that reads it while rendering produces one menu on the server and a different one in the browser.

Two rules fix it, and both appear in every guarded page after this one:

  • Read localStorage inside useEffect - effects never run on the server.
  • Hold a ready flag starting false, so the server render and the browser's first paint are identical.

Use <Link> when the user chooses to navigate - it renders a real anchor, so middle-click and "copy link address" work. Use router.push() when navigation is the result of something happening, such as logging out.

The admin link is hidden from a normal user. That is a convenience, not a permission. Type /users into the address bar as a normal user and the page loads - the server is what answers the data request with 403.

4.10 The admin user list

app/users/page.jsx is the largest file in the app because it does four things: guards the route, lists users, searches them, and deletes them. Sections 4.11 and 4.14 return to the same file for the last two.

The guard makes two checks in order - no token sends them to /login, a non-admin token sends them to /profile. Both reads happen inside useEffect behind a flag, for the reason 4.9 explained.

Nowhere in this page will you find Authorization: Bearer. The interceptor adds it. And UserTable takes callbacks, not URLs - it renders rows and calls back, so it can be dropped into any page without editing. The array is at result.data.users: the envelope is data, and this endpoint's payload has its own users key inside it.

Give the empty result its own branch. An empty list and a failed request look identical if you only render the table, and a user who searched for a name that does not exist should not think the app is broken.

4.11 Searching and paging through users

Still the same file - nothing new to create. The search box needs two pieces of state: the input's live value, and the submitted term the request actually uses. Collapse them into one and typing "alice" fires five requests, four already stale on arrival. Debouncing is the alternative, and the right answer for a search-as-you-type box.

The effect's dependency array is [page, submittedSearch], so setting state is the reload - there is no manual refetch call anywhere.

Submitting a search must also reset the page to 1. Without it, a user on page 3 who searches for a name with two matches lands on page 3 of a two-row result, sees an empty table, and concludes there are no matches. This is the most common bug in a paginated list.

Paging is done by the server: it returns one page of rows plus totalPages and total, so the browser never holds the whole table. axios also URL-encodes the params for you - a search for a&b would otherwise end the parameter early.

4.12 Viewing one user

A folder named [id] creates a dynamic segment, and useParams() reads it.

The value is always a string. id === 42 is false, and users.find((u) => u.id === id) silently finds nothing - no error, no warning, just an empty screen. Convert with Number(id) when comparing.

The page fetches by id rather than being handed the object during navigation, because a URL has to work on its own: bookmarked, refreshed, or pasted to a colleague. And it separates its failures - 401, 403, 404 and "the backend is not running" each deserve their own message, because the server already told you which one happened.

4.13 Updating a user

Prefilling is the whole difference between a create form and an edit form: a GET must finish before the form can render.

Never bind an input to undefined or null. React treats it as uncontrolled, then switches it to controlled when the data arrives, and logs a warning most people never read. The symptom is an input that ignores what you type. Start the form object as null and render a loading state, then seed every field with ?? '' - the server stores a missing phone as null.

Keep loading (the GET) and saving (the PUT) as separate flags; they mean different things to the user. The id goes in the URL because it identifies the resource, the changed fields go in the body because they are the content, and the token goes in the header courtesy of the interceptor. PUT replaces the resource, PATCH updates part of it.

The role dropdown is the interesting field: changing user to admin is how a second administrator gets created, since registration always produces a normal user.

4.14 Deleting a user

A DELETE carries no body - the id in the URL is the entire request, and the server answers with data: null because there is no resource left to return.

Do not use window.confirm. It blocks the thread, cannot be styled, its wording belongs to the browser, tests have to reach outside the page to dismiss it, and it cannot render the user's name. A piece of state and two branches give you a confirmation that is part of your app.

After a successful delete the local array is stale. Refetching costs one request and is always right; removing the row locally is instant but wrong if the delete actually failed - and it leaves the total count and the page count lying. This app refetches, and steps back a page when the last row on a page disappears.

4.15 The normal user: their own profile, and nothing else

Log in with an account registered in 4.7 and the same application becomes one page showing one record.

GET /api/auth/me takes no id. The server reads the token, finds the id inside it, and returns that record - there is no parameter to tamper with. An endpoint that derives identity from the token instead of from the request cannot be made to return the wrong person. This page's guard therefore checks only for a token, not for a role: both kinds of user are allowed here.

This backend gives a normal user no way to change their own name, email or phone. The only route that updates those fields is PUT /api/users/:id, and it sits behind adminMiddleware - a non-admin calling it gets 403 whether the call comes from your form or from the console. So the profile page is read-only apart from the photo, and it says so. Building an edit form here would produce a page that looks like it works and fails on submit for every user who is not an admin. Self-service edits belong on the server: a PUT /api/auth/me route that takes the id from the token, exactly as getMe does.

The photo upload is the one request in the app that is not JSON - a file goes into a FormData under the key photo, and the content type becomes multipart/form-data.

Prove the boundary to yourself: as a normal user the Users link is absent; typing /users anyway bounces you back via the guard; calling the endpoint from DevTools returns 403 Access denied. Admins only. The first two are your UI being helpful. The third is the thing that actually protects the data.

Chapter 5 - Common Interview Questions

Everything below is answerable from the two projects in this book. Where a question maps to a section, the section is named - if an answer does not feel solid, go back and run that lesson rather than memorising the sentence.

Interviewers rarely want the definition. They want the reason and the trade-off. "A key helps React identify list items" is a memorised answer; "without stable keys React matches by position, so inserting at the top makes it reuse the wrong DOM nodes and input state jumps rows" is an understood one.

5.1 React Fundamentals

QuestionAnswer
What is a component?A function that returns JSX and can be reused like a custom tag.
Why must component names start with a capital letter?React treats lowercase JSX tags as built-in HTML elements, so <welcomeCard /> renders an unknown HTML tag instead of your component.
Props vs state?Props are read-only input from a parent. State is data the component owns and can change. Props flow down; state stays put.
Why can a child not change its props?Data flows one way. If a child could rewrite its input, no parent could reason about its own state. The parent passes a callback down instead.
Why do lists need keys?Keys let React match items across renders. Without them it matches by position, so inserting at the top makes every row reuse the wrong DOM node and any typed input follows the wrong item.
Why not use the array index as a key?It works only while the list never reorders, filters, or has items removed - which is exactly when keys matter.
What is a Fragment and why use one?<>...</> groups siblings without adding a wrapper element, which matters when a stray <div> would break a table row or a flex layout.
Why className and not class?class is a reserved word in JavaScript. JSX compiles to JavaScript, so it uses className.
Controlled vs uncontrolled input?Controlled means React state holds the value and an onChange updates it. Uncontrolled leaves the value in the DOM. Controlled is what lets you validate, prefill, disable and reset. (4.4)
Why does a form submit handler start with e.preventDefault()?Without it the browser does a full page reload, discarding React state and the request you just started. (4.4)

5.2 Hooks

The last three rows cover hooks chapter 3 deliberately does not teach. Knowing what they are for is enough to answer honestly - "I have not needed one yet, and here is when I would" is a better answer than a memorised definition you cannot back up.

QuestionAnswer
What are the rules of hooks?Call them only at the top level of a component or custom hook - never in a loop, condition, or nested function. React tracks hooks by call order, so a conditional hook shifts every later hook by one.
Why does state need a setter instead of assignment?Assigning to a variable changes nothing React can see. Calling the setter is what schedules a re-render.
Why setCount(c => c + 1) rather than setCount(count + 1)?The updater form reads the latest value. The direct form captures the value from the render it was written in, so two updates in one tick lose one.
What does the dependency array do?No array - the effect runs after every render. [] - once, after the first render. [x] - whenever x changes. (4.2, 4.10)
What happens if you fetch in an effect with no array?The response sets state, the state change re-renders, the render re-runs the effect, and it fetches forever. (4.1)
When do you need a cleanup function?Timers, subscriptions, listeners, and in-flight requests - anything that would keep running or call setState after the component is gone.
useRef vs useState?Both survive re-renders; only state triggers one. Use a ref for DOM access or a value you need to remember but not display.
When is useContext the right tool?When many components at different depths need the same value and threading props through every level has become the bigger problem.
useReducer over useState?When updates arrive as named actions and several fields change together, keeping the transitions in one pure function is easier to follow than scattered setters.
What do useMemo and useCallback actually do?They cache a value and a function reference between renders. They are optimisations, not correctness tools - reach for them when a computation is genuinely expensive or a memoised child depends on a stable reference.

5.3 Next.js and the App Router

QuestionAnswer
How is a route created?A folder under app/ containing a page.jsx. The folder path is the URL.
What is a dynamic route?A folder named [id]. Its value is read with useParams() - and it is always a string, so === against a numeric id fails. (4.11)
What does 'use client' do?Marks the file as a Client Component so hooks, event handlers and browser APIs can run. Without it the file is a Server Component. (4.1)
Server Component vs Client Component?Server Components render on the server and ship HTML - no state, no effects, no handlers, no browser APIs. Client Components run in the browser and can do all of it. Server is the default.
Why is the default Server?Less JavaScript reaches the browser. You opt into client-side code only where interactivity actually needs it.
<Link> vs router.push()?<Link> for navigation the user chooses, so it renders a real anchor. router.push() for navigation that is the result of something happening, like a successful login. (4.6, 4.7)
Where does useRouter come from?next/navigation in the App Router. next/router is the Pages Router import and throws at runtime here.
What does the NEXT_PUBLIC_ prefix mean?The variable is exposed to the browser bundle. Without it the value is server-only and reads as undefined in a Client Component. Never prefix a secret. (4.3)
What is a hydration mismatch?The server-rendered HTML differs from the browser's first render. Reading localStorage or the current time during render causes it. Read those inside useEffect. (4.7)
What is a layout for?Shared UI that wraps a route and its children and does not remount on navigation between them.

5.4 Working with APIs

QuestionAnswer
Does fetch throw on a 404?No - and this is the most common mistake. It rejects only when the request never completed. A 404 resolves with res.ok === false, so you must check and throw yourself. (4.2)
Why put setLoading(false) in finally?It must run whether the request succeeded or failed. In the try alone, a failure leaves the spinner on forever. (4.2)
What three states does a request have?Loading, error, and data. Rendering only the third is what makes a list flash empty on load. (4.2)
What does a POST need that a GET does not?method, a Content-Type: application/json header, and a JSON.stringify-ed body. Miss the header and Express leaves req.body empty. (4.4)
fetch vs axios?axios parses JSON for you, rejects on non-2xx, encodes query params from an object, and supports interceptors. fetch is built in and needs no dependency. (4.9)
What is an interceptor?A function that runs on every request or response, so a cross-cutting rule - attach the token, handle a 401 - is written once rather than at every call site. (4.9)
Why a services/ layer?Components stop knowing URLs. Moving an endpoint becomes a one-line change in one file instead of a search across the codebase. (4.9)
What is CORS?Browsers block requests to a different origin unless the server opts in with the right headers. It is enforced by the browser, not the server, which is why the same request works from a REST client.
Why reset the page number when the search term changes?Otherwise a user on page 3 searches for something with two matches and lands on an empty page. (4.10)
Why refetch after a delete?The server is the source of truth and the local array is now stale. The alternative, removing the row locally, is instant but wrong if the delete actually failed. (4.13)
Client-side or server-side pagination?Server-side here - the server returns one page plus a total count, so the browser never holds the whole table. Client-side only suits small, fully-loaded lists. (4.10)

5.5 Authentication and Authorization

QuestionAnswer
Authentication vs authorization?Authentication is who you are - login. Authorization is what you may do - the admin check. The two middlewares in the backend are exactly this split.
401 vs 403?401 - I do not know who you are; the token is missing or expired. 403 - I know who you are and you still may not do this. (4.8)
What is a JWT?A signed string issued at login. Sending it back identifies you without the server storing a session. Signed, not encrypted - readable by anyone, so it must hold nothing secret. (4.6)
Why localStorage rather than useState for the token?State dies on refresh, which would log the user out on every F5. (4.6)
What are the risks of localStorage?Any JavaScript on the page can read it, so an XSS bug leaks the token. An httpOnly cookie is not readable by JavaScript but brings CSRF concerns of its own. Neither is free.
Is hiding an admin button enough?No. It is a convenience. Anyone can call the endpoint directly from DevTools - the server's middleware is the real boundary. (4.7)
Then why validate or guard on the client at all?Speed and clarity for the honest user. It is never the thing standing between an attacker and your data. (4.5)
How does logout work with a stateless token?There is nothing to tell the server. Logging out is deleting the token locally. Real revocation needs short expiry plus a refresh token, or a server-side denylist.
Where should an expired token be handled?Once, centrally - the axios response interceptor clears storage on any 401 instead of every component checking. (4.9)

5.6 Explain This Project

"I built a Next.js App Router learning project in two halves. The first is a set of focused lessons - components, props, JSX, conditional rendering, lists, events, and the common hooks - where each route demonstrates one concept and the code panel reads the real source off disk, so the book and the running app can never drift. The second half is a working frontend against an Express + MySQL API with JWT auth and two roles: registration, login with a role-based redirect, an authenticated user list with search and pagination, and view, update and delete for admins. It starts with plain fetch so the raw HTTP is visible, then moves to an axios client with interceptors once the repetition has made the case for it."

Two follow-ups worth having ready. What was the hardest part? - a concrete answer beats a modest one: the hydration mismatch from reading localStorage during render, and why moving it into useEffect fixes it. What would you do next? - route protection in middleware rather than per-page, a refresh-token flow, and replacing the hand-rolled loading and error state with a data-fetching library.
